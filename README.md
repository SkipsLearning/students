# Единая нейросетевая модель кредитного скоринга

Модель оценивает PD (вероятность дефолта) заёмщика. Несколько источников данных объединяются на уровне **эмбеддингов**, а не скалярных скоров. Архитектура ориентирована на подход «единой нейросетевой модели кредитного скоринга» на эмбеддингах доменных моделей.

Проект запускается сразу на синтетических данных. Для публичного датасета Kaggle [Home Credit Default Risk](https://www.kaggle.com/competitions/home-credit-default-risk/data) есть готовый адаптер.

## Задача банка

Постановка — соревнование Альфа-Банка [«DL Fintech: кредитный скоринг по данным БКИ»](https://ods.ai/competitions/dl-fintech-bki): предсказать дефолт клиента **только по кредитной истории**, метрика — ROC AUC. Банк противопоставляет два подхода:

* **стандартный** — классические модели (логистическая регрессия, бустинг) на агрегатах истории;
* **альтернативный** — рекуррентная нейросеть на последовательности кредитов «как есть».

В проекте (`configs/alfa_bki.yaml`) одна и та же история подаётся несколькими источниками:

* `bki_seq` — последовательность кредитов, из которой доменная GRU делает эмбеддинг;
* `bki_agg` — 437 агрегатов, как в базовом решении организаторов (число кредитов и доля кредитов с каждым значением каждого признака);
* `bki_gru_cv` — прогноз ансамбля GRU, обученных по фолдам, как в решении 7-го места соревнования (стекинг).

Сравниваются стандартный подход (бустинг на агрегатах), альтернативный (GRU — одна и ансамбль по фолдам) и единая модель, объединяющая все источники. Проверка идёт **по времени**: номер заявки растёт со временем подачи, поэтому модели учатся на более ранних заявках, а оцениваются на самых поздних — как в постановке банка. Результаты — в разделе «Результаты (задача банка)».

## Быстрый старт

**Без командной строки:** двойной щелчок по `start.command` (macOS) или `start.bat` (Windows). Первый запуск ставит библиотеки в `.venv` (1–3 минуты, нужен интернет), затем в браузере открывается интерфейс. Простые страницы для всех — «Главная», «Результаты» (выводы простыми словами), «Оценить клиента» (светофор риска и вклад каждого источника), «Словарь»; раздел «Для специалистов» — обучение с параметрами и подробные отчёты всех запусков.

```bash
pip install -r requirements.txt

# 0. Веб-интерфейс (то же, что start.command)
streamlit run app.py

# 1. Обучение + оценка + базлайны + отчёт (~30 с на CPU)
python scripts/run.py --config configs/synthetic.yaml

# 2. Скоринг клиентов обученной моделью (готовая модель лежит в results/)
python scripts/predict.py --run-dir results/synthetic_reference \
       --input results/synthetic_reference/sample_requests.jsonl

# 3. Добавление нового источника: меняется только конфиг,
#    веса towers старых источников переносятся из прошлого запуска
python scripts/run.py --config configs/synthetic_new_source.yaml --warm-start runs/<прошлый_запуск>

# 4. Устойчивость прироста по нескольким seed
python scripts/multi_seed.py --config configs/synthetic.yaml --seeds 1 2 3 4 5

# 5. Тесты (метрики сверяются со sklearn, сквозные прогоны, мок Home Credit)
python -m pytest tests -q
```

## Архитектура

```
 Карты (32) ──────────┐
 Расч. счёт (64) ─────┤  нет источника → обучаемый «средний» эмбеддинг
 БКИ (256) ───────────┤
 Граф связей (768) ───┤        каждый: tower = Linear→ReLU→Dropout→Linear→ReLU
 Анкета ─ Entity Emb ─┘  (48)
            │
            ▼
   concat(выходы towers) ⊕ бинарные флаги наличия источников
            │
            ▼
   head: Linear→ReLU→Dropout→Linear→ReLU→Linear(1) → logit → σ → PD ∈ [0, 1]
```

* **Вход** — эмбеддинги с последних полносвязных слоёв обученных доменных моделей. Размерности по умолчанию: 32 / 64 / 256 / 768 / 48. Все они задаются в конфиге.
* **Пропуски.** Если источника у клиента нет, вместо его эмбеддинга подставляется константный вектор. Он инициализируется средним эмбеддингом по train и дообучается (`learned_mean`) либо фиксируется (`fixed_mean`). Флаг наличия источника подаётся в голову как отдельный признак.
* **Source dropout** (10%). При обучении доступные источники случайно «прячутся», но хотя бы один всегда остаётся. Так модель учится скорить клиента с любым непустым набором источников.
* **Табличные признаки.** Категории кодируются Entity Embeddings, размерность выбирается правилом `min(16, 1.6·k^0.56)`. Редкие значения и пропуски получают свои индексы. Числовые признаки проходят signed log1p для тяжёлых хвостов, импутацию медианой и StandardScaler или min-max. Все параметры предобработки считаются только на train.
* **Обучение.** `BCEWithLogitsLoss` (опционально `pos_weight: auto`) и Adam. Learning rate снижается через ReduceLROnPlateau, early stopping идёт по Джини на val. На val подбирается Platt-калибровка (`train.calibration: platt`, включена по умолчанию): она не меняет ранжирование и Джини, но выравнивает средний PD с фактической долей дефолтов. Особенно она нужна при `pos_weight`, который завышает PD.

## Данные и таргет

### Синтетика (`configs/synthetic.yaml`)

* У клиента есть 10 скрытых факторов риска. Истинный риск — нелинейная функция этих факторов, включающая **взаимодействия факторов, которые видны разным источникам**.
* Каждый источник видит своё подмножество факторов с шумом. Его эмбеддинг устроен как ReLU от случайной проекции этих факторов и нерелевантных признаков, то есть похож на предпоследний слой доменной модели.
* Наличие источника случайно и может зависеть от риска. Например, у рискованных клиентов чаще нет кредитной истории (`risk_coef < 0`).
* Таргет строится честно, из помесячных траекторий просрочки (DPD):
  * основной дефолт — DPD ≥ K = 90 в пределах N = 12 месяцев;
  * короткое определение — K = 30.

  Функция `default_flag` применима и к реальным траекториям DPD.
* Генератор задаёт дрейф популяции во времени, чтобы PSI был информативен.
* У каждого источника свой генератор случайных чисел. Поэтому добавление источника в конфиг не меняет ни таргет, ни остальные источники, и запуски сравнимы.
* Разбиение out-of-time по месяцам выдачи (`split.scheme: time`):

  | Часть | Месяцы | Назначение |
  |---|---|---|
  | `domain_fit` | 0–5 | обучение доменных моделей и скоров базлайна |
  | `train` | 6–15 | обучение единой модели |
  | `val` | 16–19 | early stopping и калибровка |
  | `test` | 20–23 | итоговая оценка |

### Альфа-Банк, БКИ (`configs/alfa_bki.yaml`)

```bash
# data_for_competition.zip со страницы соревнования -> распаковать в data/data_for_competition
python scripts/run.py --config configs/alfa_bki.yaml          # 500 000 самых поздних клиентов, ~15 мин, ~5.5 ГБ RAM
python scripts/run.py --config configs/alfa_bki.yaml --set data.alfa_bki.n_clients=1000000 --set data.alfa_bki.encoder_epochs=6
python scripts/run.py --config configs/alfa_bki.yaml --set data.alfa_bki.n_clients=50000 --set data.alfa_bki.cv_folds=2   # быстрая проверка
```

* 3 млн клиентов, 26 млн записей о кредитах, доля дефолтов 3.5%. Все признаки уже закодированы целыми кодами.
* **Время.** Дат в данных нет, но номер заявки растёт со временем: с ростом id плавно меняются признаки (например, кредитов на клиента — от 7.9 у первых id до 9.8 у последних), а test соревнования похож на самые поздние заявки. Поэтому берутся самые поздние клиенты (`take: latest`), они делятся на 24 «периода» по порядку id, и разбиение идёт по времени: domain_fit — самые ранние, test — самые поздние (`split.scheme: time`).
* У `test_data` соревнования нет ответов, поэтому качество меряется на самой поздней части `train_target`.
* Доменная GRU получает каждый кредит как набор категориальных кодов, у каждого признака свой обучаемый эмбеддинг (`CategoricalInput` в `data/sequence_encoder.py`). Берутся последние 32 кредита — этого хватает 99.9% клиентов. Её эмбеддинги — out-of-sample, потому что она учится только на domain_fit.
* **GRU по фолдам** (`cv_folds: 5`): клиенты domain_fit + train делятся на 5 частей, каждая GRU учится на четырёх. Клиент обучающей части получает прогноз модели, которая его не видела (out-of-fold), клиенты val/test — среднее пяти моделей. Эмбеддинги так объединять нельзя (у каждой модели своё пространство), поэтому в единую модель идёт прогноз — это стекинг.
* Бустинг на агрегатах для честного сравнения учится на тех же domain_fit + train (`baselines.single_source_data`).
* Агрегаты считаются блоками по 250 000 клиентов, чтобы one-hot 26 млн кредитов не занимал память целиком. Полный объём (`n_clients: null`) по оценке не помещается в 16 ГБ памяти и не проверялся.

### Home Credit (`configs/home_credit.yaml`)

```bash
kaggle competitions download -c home-credit-default-risk   # нужно принять правила соревнования
unzip home-credit-default-risk.zip -d data/home-credit-default-risk
python scripts/run.py --config configs/home_credit.yaml
# быстрая отладка: --set data.home_credit.nrows=50000
```

| Источник | Таблицы | Последних событий |
|---|---|---|
| `tabular` | application_train (+ производные отношения: кредит/доход и др.) | — |
| `bki` | bureau + агрегаты bureau_balance по каждому кредиту | 32 |
| `card` | credit_card_balance | 24 мес. |
| `account` | installments_payments (аналог расчётного счёта) | 48 |
| `prev_app` | previous_application | 16 |
| `pos` | POS_CASH_balance (выключен, включается `enabled: true`) | 24 мес. |
| `graph` | в датасете отсутствует, выключен | — |

Схема двухэтапная:

1. По каждой таблице на части `domain_fit` (30% выборки) обучается доменная GRU-модель на PD.
2. Эмбеддинг клиента снимается с её предпоследнего слоя и подаётся в единую модель. Единая модель обучается на `train`.

Благодаря такому разделению эмбеддинги на train/val/test — out-of-sample для доменных моделей.

**Ограничения датасета:**

* дат выдачи нет, поэтому разбиение стратифицированное случайное, а не out-of-time;
* `TARGET` задан организаторами («проблемы с оплатой») и не совпадает с определением 90+ за 12 месяцев;
* короткое определение дефолта построить нельзя.

Адаптер проверен на реальных таблицах (полный датасет: 307 511 заявок) и на мок-данных той же схемы (`tests/mock_home_credit.py`). Полный прогон занимает около 3.5 минут на 10-ядерном CPU и до 4.7 ГБ памяти. Результаты — в разделе «Результаты» ниже и в `results/home_credit_full/`.

## Добавление нового источника

Изменения затрагивают только конфиг и данные, ядро модели не меняется:

1. **Опишите источник в конфиге.** Добавьте элемент в `sources`: имя, `dim` и `tower`. Можно наследовать базовый конфиг через `base:` (см. `configs/synthetic_new_source.yaml`).
2. **Передайте эмбеддинг источника в данных.**
   * Синтетика: блок `synthetic` в описании источника.
   * Home Credit: функция-построитель в `TABLE_BUILDERS` и ключ `home_credit.table`.
   * Собственные данные: массив `embeddings[name]` и маска `masks[name]` в `ScoringData`.
3. **Переобучите только общую модель.** Доменные модели остальных источников не трогаются. Флаг `--warm-start` переносит веса towers и заглушек старых источников, у которых совпадают имена и формы тензоров.

## Инференс

```python
from unified_scoring.inference import Scorer

scorer = Scorer.from_run_dir("results/synthetic_reference")
pd_ = scorer.predict([
    {"client_id": "1", "embeddings": {"card": [...32 числа...], "bki": [...256...]},
     "tabular": {"region": "REG_07", "income": 55000, "age": 34}},
    {"client_id": "2", "embeddings": {"account": [...64...]}},  # только один источник
])
```

* Источники, которых нет, просто не передаются.
* Табличные поля можно передавать частично: недостающие обрабатываются как пропуски.
* Модель возвращает ошибку, если неверна размерность эмбеддинга, имя источника неизвестно или у клиента нет ни одного источника.

## Базлайны

| Базлайн | Что проверяет |
|---|---|
| LR на векторе скоров | классическая схема: доменный скор на источник → логистическая регрессия |
| LR на эмбеддингах | дают ли что-то сами эмбеддинги без нелинейного смесителя |
| Бустинг на векторе скоров | не слишком ли слаб линейный смеситель скоров |
| Бустинг на эмбеддингах | сильный нелинейный конкурент на том же входе, что у единой модели |

Бустинг — `HistGradientBoostingClassifier`, число деревьев подбирается по Джини на val (как early stopping у нейросети). Отключается `--set baselines.boosting=false`.

## Метрики

Все метрики реализованы в `unified_scoring/metrics.py` на numpy; совпадение со sklearn проверяется тестами.

* **Джини** = 100·(2·AUC − 1), в %. Это основная метрика.
* **ROC AUC** считается через ранговую статистику Манна–Уитни, совпадающие значения скора получают средние ранги.
* **KS** = max|TPR − FPR|, в %.
* **PR-AUC** — average precision.
* **Brier score** — оценка калибровки.
* **PSI** — стабильность распределения PD: train→val и train→test.
* **Значимость прироста** — парный бутстрэп разницы Джини на test (1000 повторов): 95%-интервал и p-value для сравнения единой модели с каждым базлайном.

Отчёт дополнительно содержит:

* Джини по числу доступных у клиента источников;
* падение Джини при «выключении» каждого источника;
* долю дефолтов среди одобренных при уровне одобрения 50–90%.

## Результаты (задача банка: БКИ Альфа-Банка)

Подробности: `results/alfa_bki_1m/REPORT.md` (1 млн самых поздних клиентов) и `results/alfa_bki_reference/REPORT.md` (500 тыс., конфиг по умолчанию).

Проверка по времени: модели учатся на более ранних заявках, оцениваются на самых поздних 17% (как в постановке банка).

| Подход | ROC AUC, 500 тыс. | ROC AUC, 1 млн | Джини, 1 млн |
|---|---:|---:|---:|
| Бустинг на агрегатах (стандартный подход; domain_fit + train) | 0.7412 | 0.7405 | 48.10 |
| Одна GRU на сырой истории (обучена на domain_fit, ~29%) | 0.7292 | 0.7462 | 49.23 |
| **GRU по фолдам — ансамбль из 5 (альтернативный подход; domain_fit + train)** | **0.7564** | **0.7586** | **51.73** |
| Единая NN: эмбеддинг GRU + агрегаты + прогноз GRU по фолдам | 0.7473 | 0.7532 | 50.64 |
| LR на векторе скоров | 0.7532 | 0.7550 | 51.01 |
| Бустинг на всех эмбеддингах + агрегатах | 0.7526 | 0.7556 | 51.12 |

Ключевые сравнения (разница Джини, п.п., 95% бутстрэп-интервал):

| Сравнение | 1 млн | 500 тыс. |
|---|---:|---:|
| GRU по фолдам против бустинга на агрегатах | **+3.63 [+2.90; +4.44]** | **+3.03 [+1.97; +4.11]** |
| Одна GRU против бустинга на агрегатах | **+1.13 [+0.37; +1.94]** | −2.40 [−3.77; −1.03] |
| Единая NN против бустинга на агрегатах | **+2.54 [+1.85; +3.31]** | +1.22 [+0.04; +2.27] |
| Единая NN против GRU по фолдам | −1.09 [−1.44; −0.69] | −1.81 [−2.68; −0.94] |

Для сравнения — другие решения этой задачи: блендинг классических моделей на агрегатах (проект Wiruto) — 0.756 на отложенной выборке и 0.743 на Kaggle; 7-е место соревнования (стекинг 6 нейросетей и 3 бустингов на всех 3 млн клиентов) — 0.7775. Выборки разные, поэтому сравнение ориентировочное.

* **Ответ на вопрос банка:** рекуррентная сеть на сырой истории лучше бустинга на агрегатах, если обучать её на всех данных — ансамблем по фолдам: +3.6 п.п. Джини на 1 млн клиентов (AUC 0.759 против 0.741). Даже одна GRU обгоняет агрегаты, когда данных достаточно (1 млн), и проигрывает при 500 тыс.: нейросеть сильнее зависит от объёма данных.
* **Объединение здесь не помогает.** Единая модель лучше стандартного подхода (+2.5 п.п.), но хуже GRU по фолдам самой по себе (−1.1 п.п.). То же со всеми смесителями (LR, бустинг): добавление агрегатов к GRU не даёт прироста. Агрегаты — производная от той же последовательности кредитов, новой информации в них нет. Единая модель полезна, когда источники действительно разные (как на синтетике); в задаче банка источник один.
* **Проверка по времени важна.** При случайном разбиении на ранних клиентах те же модели показывали AUC 0.77–0.78; при проверке на будущих заявках — 0.74–0.76. Случайное разбиение завышает качество.
* **Сильный базлайн важен.** С упрощёнными 80 агрегатами бустинг давал на 1.8 п.п. AUC меньше, чем с полными 437.

## Результаты (синтетика, out-of-time)

Подробности: `results/synthetic_reference/REPORT.md` и `results/multi_seed_summary.md`.

| Test, дефолт 90+ / 12 мес. | Джини, % (seed 42) | Δ к единой NN, 95% интервал | Джини, % (5 seed) |
|---|---:|---:|---:|
| **Единая NN (эмбеддинги)** | **64.47** | — | 63.21 ± 2.23 |
| Бустинг на эмбеддингах | 64.57 | −0.10 [−2.13; +2.17] | 63.48 ± 1.78 |
| LR на векторе скоров (базлайн) | 60.63 | +3.85 [+1.50; +6.02] | 60.01 ± 2.42 |
| LR на эмбеддингах | 60.60 | +3.87 [+1.96; +5.88] | 60.41 ± 1.33 |
| Бустинг на векторе скоров | 59.89 | +4.58 [+2.19; +6.96] | 59.63 ± 2.14 |

* **Объединение эмбеддингов лучше объединения скоров:** единая NN выигрывает у всех моделей на скорах +3.9…+4.6 п.п., интервал не включает ноль. По 5 seed прирост к базлайну +3.2 ± 1.2 п.п. (основной таргет) и +3.1 ± 1.3 п.п. (короткий, 30+), положительный во всех запусках.
* **Нужен нелинейный смеситель:** LR на эмбеддингах не лучше базлайна. Бустинг на эмбеддингах даёт тот же Джини, что и единая NN (разница незначима). Выбор нейросети обоснован не приростом Джини над бустингом, а архитектурой: модульность, warm start, работа с отсутствующими источниками (см. `docs/RATIONALE.md`).
* **Стабильность:** PSI ≤ 0.008 у всех моделей.
* **Обоснование и бизнес-эффект:** [`docs/RATIONALE.md`](docs/RATIONALE.md).

## Результаты (реальные данные Home Credit)

Подробности: `results/home_credit_full/REPORT.md`. Разбиение стратифицированное случайное (дат выдачи в датасете нет).

| Test, Home Credit, 307 511 заявок | Джини, % | Δ единой NN, 95% интервал |
|---|---:|---:|
| Единая NN (эмбеддинги) | 55.16 | — |
| Бустинг на эмбеддингах | **56.86** | −1.70 [−2.31; −1.06] |
| LR на эмбеддингах | 56.21 | −1.05 [−1.66; −0.41] |
| Бустинг на векторе скоров | 54.74 | +0.42 [−0.17; +1.00] |
| LR на векторе скоров (базлайн) | 54.73 | +0.43 [−0.13; +1.01] |

* **Главный тезис подтверждается:** при одинаковом смесителе эмбеддинги значимо лучше скоров. LR: +1.48 п.п. [+0.81; +2.15], бустинг: +2.12 п.п. [+1.43; +2.79].
* **Нейросеть-смеситель здесь не лучший выбор:** она лишь на уровне базлайна (+0.4 п.п., незначимо) и уступает LR и бустингу на тех же эмбеддингах. Настройка гиперпараметров по val (lr, weight decay, dropout, source dropout, размер Entity Embeddings) подняла Джини на val не больше чем на 0.3 п.п. Вероятная причина: в реальных данных почти весь сигнал даёт анкета (её выключение стоит −10.8 п.п.), а взаимодействий между источниками мало, поэтому гибкость нейросети не окупается и она быстро переобучается (лучшая эпоха — 4-я).

## Воспроизводимость

* **Seed** фиксируется во всех генераторах (`random`, `numpy`, `torch`, cuDNN). Повторный запуск с тем же seed на CPU даёт те же метрики.
* **Гиперпараметры** пишутся в `train.log` и `config.yaml` каждого запуска.
* **Версии:** проверено на Python 3.12 с torch 2.14, scikit-learn 1.9, pandas 3.0, numpy 2.5 и streamlit 1.65. На других версиях torch метрики могут отличаться в сотых долях п.п. из-за численных различий.
